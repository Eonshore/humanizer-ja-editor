# 評価方法

`benchmark.jsonl` は、humanizer-ja-editorの回帰試験用仕様です。文章が「人間に見えるか」ではなく、次の5軸を評価します。
`document` モードでは、これに加えて、主張が根拠段階を越えないことと、コードの並びではなく読者の問いに沿って説明することを必須条件にします。

## 評価軸

| 軸 | 内容 | 配点 |
|---|---|---:|
| 保真 | 数字、主体、極性、確度、条件、引用を維持したか | 0〜4 |
| 非捏造 | 元文にない事実、体験、感情、出典を追加していないか | 0〜4 |
| 場面適合 | chat、技術文書、学術、小説などの用途に合うか | 0〜3 |
| 編集判断 | 直すべき箇所を直し、残すべき箇所を残したか | 0〜3 |
| 表現 | テンプレ感と冗長さを減らし、文同士の関係を読み違えにくいか | 0〜2 |

合計16点。保真または非捏造が0点の場合、合計点にかかわらず失敗とします。

### document モードの必須条件

- 設計・文書上の主張、ソースの存在、到達可能な経路、テストまたは再現、測定、実行中または利用者に見える運用を混同しない。
- 作者の声のサンプルと説明構造のサンプルを、対象の事実、実装、性能、到達状態の根拠にしない。
- 概念解説では、本文をディレクトリ順、モジュール順、関数順にしない。
- 公開契約、必要な証拠アンカー、または省くと曖昧になる識別子だけを本文に残す。
- APIリファレンス、モジュール参照、呼び出し経路を明示的に求めるケースでは、この例外を認める。
- 目的、読者、根拠が不足する場合は、狭い仮定をラベル付けするか、アウトラインと証拠の不足箇所を返す。

### 初心者向け技術説明プロファイルの必須条件

- 読者が何について初心者なのかを必要な範囲で定め、理解力まで低いとは扱わない。
- 用語を隠さず、必要になる理由、資料に支えられた最小ケース、正式な用語または仕組みへ順に橋渡しする。
- 暫定的な単純化や心的モデルを最終定義にせず、条件、例外、根拠段階へ戻す。
- 比喩には目的、対応関係、限界を持たせ、対象の事実、定義、因果の代わりにしない。
- 実際に提示しない図、アニメーション、クリック、スライダーを参照しない。
- 説明構造サンプルから、対象外の技術事実、企業情報、著者固有の口癖、一人称の体験、販促表現を持ち込まない。
- 初心者向けを理由に、公開API、CLI、設定キー、条件、例外、安全上の注意を削除しない。

### ガイド付きチュートリアルプロファイルの必須条件

- 到達点、開始状態、主要経路、操作、観察、失敗分岐、条件つき完了を資料の範囲で追えるようにする。
- 手順、期待される出力、出力例、実行記録を区別し、手順の記載を実行済みまたは成功済みへ言い換えない。
- コマンド、コード、識別子、版、順序、秘密情報のプレースホルダー、安全条件を保持する。
- 観察方法がない場合は出力や画面を推測せず、不足資料または確認不能として残す。
- 文書化を、外部公開、課金、秘密情報入力、削除、本番変更の権限へ読み替えない。
- 概念説明、APIリファレンス、原因切り分けだけの依頼を、無理にチュートリアル化しない。

### トラブルシューティングプロファイルの必須条件

- 期待、症状、観察、仮説、原因判断、回避策、修正、再検証、rollbackを必要な範囲で分ける。
- 設定、静的な到達可能性、現在の実行状態、利用者向け動作を別の証拠として扱う。
- 相関を原因へ昇格させず、原因確度を証拠の強さに合わせる。
- 診断、修正提案、変更実行の権限境界を守り、診断依頼から変更を実施済みへ変えない。
- 回避策を根治とせず、修正後は元の症状、実行状態、利用者向け動作、最小回帰を確認する。
- rollback不能または部分復元しかできない場合、その境界を隠さない。

### 比較・選定プロファイルの必須条件

- 判断課題、利用条件、候補、現状維持案、必須条件、共通評価軸を必要な範囲で定める。
- `met`、`not_met`、`unknown`、`not_applicable`を区別し、未知を0点または劣位へ変換しない。
- 候補間で版、プラン、入力、環境、期間、測定方法が違う場合、同条件の順位として扱わない。
- 重み、点数、順位は、ユーザーまたは合意済み基準に根拠がある場合だけ使用する。
- 導入時だけでなく、必要に応じて運用、更新、撤退、再評価を扱う。
- 推奨の強さ、証拠の確かさ、最終決定、購入・導入などの実行権限を分ける。

### なんJスレッド風プロファイルの必須条件

- 明示指定時だけ使い、通常編集やGitHub・Slack・Xのスレッドへ混入させない。
- レス番号とアンカーを整合させ、話者間の返答と発言の長短を使う。語尾だけの変換や、定型ネタの機械的な連打を避ける。
- 架空の話者、質問、相づち、レス番号を依頼された演出として評価する。これだけを非捏造違反としない。
- 対象の数字、確度、主体、条件、コード、引用、出典を保持し、架空話者の体験や世評を根拠にしない。
- タイトルでも断定を強めず、重要な限定を遠い末尾だけに追いやらない。
- `annotation`、口調だけ、行数や範囲の維持など、より具体的な指示に従う。

## ケース形式

各JSON行には次が含まれます。

- `id`: ケースID
- `scene`: 文書場面
- `mode`: rewrite / annotation / edit / document
- `should_edit`: 編集すべきか
- `input`: 入力文
- `must_preserve`: 必須保持情報
- `expected_actions`: 期待する編集判断
- `forbidden_actions`: 禁止動作
- `scope`: 必要なケースだけ編集範囲
- `author_sample_note`: 必要なケースだけ作者サンプル条件
- `explanation_profile`: 必要なケースだけ `beginner` などの説明プロファイル
- `purpose_profile`: 必要なケースだけ `guided-tutorial` / `troubleshooting` / `comparison-selection` の目的プロファイル
- `style_profile`: 明示指定のケースだけ `nanj-thread`。文体を使わない対照ケースには付けない

`document` ケースの `input` には、依頼文と、根拠・事実資料、作者の声のサンプル、説明構造のサンプルを一つの再現可能な入力として含める。
被験モデルには、サンプルの役割を明示してもよいが、期待される結論や禁止動作は見せない。

## 推奨する実行方法

1. 被験モデルには `SKILL.md` と必要なreferencesだけを読ませる。`document` ケースでは `software-exposition.md` を含め、`explanation_profile` が `beginner` の場合は `beginner-explanation-profile.md` を、`purpose_profile` がある場合は対応する目的プロファイルを含める
2. `input`、`scene`、`mode`、`scope`、`author_sample_note`、`explanation_profile`、`purpose_profile`、`style_profile`だけを与える。`style_profile` がある場合は対応する参照文書も読ませる
3. `must_preserve`、`expected_actions`、`forbidden_actions`はjudgeだけが読む
4. 出力を人間または別モデルで採点する
5. 失敗を規則か評価ケースへ反映する

期待事項を被験モデルへ見せると、規則ではなく答えを暗記する評価になるため避けてください。

## 静的監査

rewriteケースでは、入力と出力を一時ファイルへ保存し、次も実行できます。

```bash
python scripts/protect_audit.py input.txt output.txt --strict
```

この監査は数字やコードの差分を見つけますが、主体の入れ替わりや因果関係の変化は判定できません。
なんJスレッド風では、レス番号・アンカーを本文の数量と区別します。監査用コピーで特定済みの構造行を除くことはできますが、本文やコードの数字を一括削除してはいけません。

## 追加すべきケース

実運用で次が起きたら、最小の再現例を追加します。

- 数字や日付が消えた
- 主体が入れ替わった
- 可能性が断定になった
- 技術用語を平易化しすぎた
- 小説の文体を均した
- 機能的な箇条書きを散文へ変えた
- 作者サンプルにない口癖を増やした
- 空話を削った後、架空情報で長さを戻した
- 対比、例外、因果の関係を読み違えやすいまま残した
- 読者に生じた疑問を放置し、後方の既存情報を安全に移せたのに移さなかった
- 指示語の受け先を曖昧にした、または明確な指示語を機械的に削除した
- 問題から改善への移り目を示すために、原文にない負担や利点を足した
- 定義済みの用語を、AIらしく見えるという理由だけで削除した
- リポジトリの説明を、ディレクトリ、モジュール、関数の順の単なるウォークスルーにした
- 作者の声または説明構造のサンプルから、対象外の技術事実や性能を持ち込んだ
- ソースの存在を、テスト済み、測定済み、実行中、利用者に見える状態へ言い換えた
- 公開APIやCLIを一般名へ置き換え、内部ヘルパーを本文へ過剰に残した
- 目的、読者、根拠が不足しているのに、もっともらしい完成文を捏造した
- APIリファレンスや呼び出し経路を明示的に求められたのに、概念解説の規則だけで構造を消した
- 初心者向け説明で、対象分野の初心者と理解力が低い読者を混同し、幼児語、過剰な称賛、感嘆符で語調を作った
- 暫定的な単純化や比喩を、正式な用語、条件、仕組みへ戻さなかった
- 実際には提示していない図、クリック、スライダー、アニメーションを参照した
- 説明構造サンプルから、著者の口癖、一人称の体験、企業や製品の情報を対象へ持ち込んだ
- 初心者向けを理由に、公開API、条件、例外、根拠の限定を削除した
- チュートリアルの手順を、実行済み、成功済み、画面確認済みへ言い換えた
- 観察方法がないのに、期待出力、画面、既知でない失敗分岐を作った
- 非手順文書を、番号と命令形だけのチュートリアルへ変えた
- 診断依頼から修正、再起動、設定変更を実施済みへ変えた
- 設定済み、実行中、利用者に見える状態を同じ証拠として扱った
- 相関を原因へ、回避策を根治へ言い換えた
- 比較で未知を0点または劣位にし、根拠のない重み、総合点、順位を作った
- 異なる版、プラン、環境、測定条件を同条件の比較として扱った
- 比較結果を、購入、導入、承認済みの決定へ言い換えた

「AIっぽい単語が残った」だけでなく、誤修正しなかったかを同数以上評価することが重要です。
