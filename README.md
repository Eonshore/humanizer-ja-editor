# Humanizer JA Editor

日本語文章を、事実・数字・責任主体・専門用語・不確実性・書き手の声を保ちながら編集するAgent Skillです。

文章や資料を渡し、何をしてほしいかを一つ伝えれば使えます。通常は、モード名、場面名、編集強度を指定する必要はありません。

単なる禁止語集でも、AI生成判定器でもありません。文章の用途を判定し、変更してはいけない情報を先に保護してから、テンプレ感、過剰な説明、語域の混在、均一なリズムを直します。

## まず使う

### 文章を自然にする

文章を貼り、次のように依頼します。

```text
この文章を、事実と語調を変えずに自然な日本語へ直してください。
```

### 問題点だけを見る

全文を書き換えず、重要な問題だけを確認できます。

```text
この文章を監査し、重要な問題点だけを示してください。
```

### 資料から技術を説明する

リポジトリ、コード、テスト、設計資料、既存文書、ベンチマーク出力、ログなどを根拠に、技術や設計を説明する文書を作れます。

```text
このリポジトリを根拠に、コードの列挙ではなく、どの問題をどのような考え方で扱う技術なのかを説明してください。未検証の動作や性能は主張しないでください。
```

### 読者の作業や判断に合わせる

順序付きのチュートリアル、原因を切り分けるトラブルシューティング、条件つきの比較・選定にも対応します。

```text
この導入資料から、開始状態、操作、確認結果、失敗時の戻り先が分かるチュートリアルを作ってください。実行済みとは書かないでください。
```

```text
この障害メモを、症状、観察、仮説、原因の確度、回避策、再検証に分けて整理してください。診断だけで、修正は実行しないでください。
```

```text
候補A、候補B、現状維持を、必須条件と同じ評価軸で比較してください。情報がない項目は0点にせず、未知として残してください。
```

### なんJのスレッド風にする

レス番号、`>>2` のようなアンカー、短レスと説明レスの掛け合いを使った、架空のスレッドへ変換できます。
「なんJ風」と指定した場合だけ使います。通常の文章編集の語調は変わりません。

```text
$humanizer-ja-editor で、以下の文章をなんJのスレッド風にしてください。
8レスくらいで、猛虎弁と軽いボケ・ツッコミを入れつつ、内容が分かる感じに。
数字、条件、未確認の点は残してください。
```

「ノリを濃いめに」「口調は控えめでスレ形式を中心に」「番号を付けず口調だけ」なども指定できます。
架空の話者の反応は演出として加えますが、実在の投稿や評判、資料にない検証体験は作りません。
文体と出力例は [なんJスレッド風プロファイル](references/nanj-thread-profile.md) を参照してください。

## 依頼で伝えること

基本的には、次の三つで十分です。

1. **対象**：貼り付けた文章、ファイル、ディレクトリ、リポジトリ
2. **目的**：完成版がほしい、問題点だけ見たい、資料から説明文を作りたい
3. **守るもの**：事実、語調、構成、専門用語、根拠の範囲など

想定読者、作者サンプル、変更してよい範囲に希望がある場合だけ追加します。指定がなければ、スキルが依頼内容から判断します。

## 必要なときだけ使う指定

| したいこと | 依頼の例 | 内部で選ばれる処理 |
|---|---|---|
| 完成版へ書き直す | 「自然な日本語へ直して」 | `rewrite` |
| 問題点だけ確認する | 「監査だけ」「先に問題点だけ」 | `annotation` |
| ファイルを直接直す | 「README.mdの導入だけ直して」 | `edit` |
| 資料から説明文を作る | 「このリポジトリを資料化して」 | `document` |
| 初心者向けに説明する | 「対象分野の初心者向けに説明して」 | 選ばれた処理に初心者向け説明方針を追加 |
| 操作できる手順へ組み立てる | 「最初の一回を案内するチュートリアルにして」 | 選ばれた処理にガイド付きチュートリアル方針を追加 |
| 不具合の証拠と原因候補を整理する | 「症状と仮説を分けて原因を切り分けて」 | 選ばれた処理にトラブルシューティング方針を追加 |
| 候補を同じ条件で比較する | 「必須条件、未知、代償を残して選定資料にして」 | 選ばれた処理に比較・選定方針を追加 |
| なんJのスレッド風にする | 「猛虎弁でレスが付くスレにして」 | 選ばれた処理に `nanj-thread` の口調・レス形式を追加 |

これらは高度な制御が必要な場合の目安です。通常の利用で、内部の名前を覚える必要はありません。

## このスキルが守ること

- 主張の肯定・否定、確度、主体、責任を変えない
- 数字、日付、単位、条件、例外、引用、コード、パス、URLを保つ
- 元の文章にない体験、感情、固有名詞、数値、出典、因果関係を追加しない
- 明示されたスレッド化・創作では、架空の話者や反応、レス番号を演出として加えられる。対象の事実や実在の人物の体験とは区別する
- 作者サンプルがある場合は、一般的な禁止則より、その書き手の声を優先する

## 詳しい機能

- 保真契約を最優先
- chat / status / technical-docs / report / academic / public-essay / fiction の場面分岐
- minimal / bounded / structural の編集範囲
- rewrite / annotation / edit / document の出力モード
- 混在資料から概念先行の技術解説を作る document モード
- 初心者を子ども扱いせず、問題、最小ケース、正確な仕組みへ橋渡しする初心者向け技術説明プロファイル
- 開始状態、操作、観察、失敗分岐、条件つき完了を分け、手順を実行済みへ変えないガイド付きチュートリアルプロファイル
- 症状、観察、仮説、原因確度、権限、live再検証、rollbackを分けるトラブルシューティングプロファイル
- 必須条件、共通評価軸、未知、証拠条件、ライフサイクル、条件つき推奨を分ける比較・選定プロファイル
- 明示指定に応じ、猛虎弁、レス番号、アンカー、話者間の掛け合いを使うなんJスレッド風プロファイル
- 作者サンプルを一般規則より優先
- 根拠・事実資料、作者の声のサンプル、説明構造のサンプルを分離
- 設計主張、ソースの存在、到達可能な経路、テスト、測定、実行中または利用者に見える状態を別の根拠段階として扱う
- 元文にない体験・感情・数字・出典を追加しない
- 長文では、文間関係、読者に生じる疑問、指示語の受け先、問題から改善への移り目を監査
- 即席の複合語や曖昧な万能動詞を、原文にある具体的な動作へ戻す
- 数字、日付、URL、コード、パス、バージョンなどを機械的に比較する補助スクリプト
- 日本語作者サンプルの文長、語尾、記号、接続表現を集計する補助スクリプト
- 誤修正を含む評価ケース

## 導入

Agent Skills互換クライアントのskillディレクトリへ、フォルダごと配置してください。`SKILL.md`だけでも基本機能は動きますが、保真規則、場面別ルール、評価ケース、補助スクリプトを使うにはフォルダ全体が必要です。

補助スクリプトはPython 3.10以上で動作し、外部パッケージを必要としません。

プロジェクト単位で使う場合の一例です。

```text
<project>/.agents/skills/humanizer-ja-editor/
```

クライアント固有の配置先がある場合は、その仕様を優先してください。

## 応用例

```text
samples/の文章を作者サンプルとして使い、draft.mdを同じ声に寄せてください。
```

```text
このリポジトリ、テスト、設計資料を根拠にして、関数の説明ではなく、どの問題をどういう考え方で扱う技術なのかを説明してください。未検証の動作や性能は主張しないでください。
```

```text
この技術を、対象分野の用語をまだ知らない読者向けに説明してください。専門語は隠さず、必要になる理由、最小の例、正確な仕組み、限界の順で橋渡ししてください。
```

```text
このセットアップ資料を、開始前の条件、操作ごとの観察、既知の失敗分岐、条件つきの完了確認を持つチュートリアルへ組み直してください。提供されていない画面や実行結果は作らないでください。
```

```text
この不具合報告を、期待と実際、観察された事実、原因候補、切り分け、現在の原因確度、回避策、修正後に必要なlive確認へ分けてください。設定済みと動作中を混同しないでください。
```

```text
候補A、候補B、現状維持を、導入、運用、更新、撤退まで含めて比較してください。重みは指定されていないため作らず、結論が変わる条件を示してください。
```

## 補助スクリプト

### 編集前後の保護対象監査

```bash
python scripts/protect_audit.py before.txt after.txt
python scripts/protect_audit.py before.txt after.txt --json
```

これは意味同一性を証明するものではありません。数字、日付、単位、URL、コード、パス、バージョン、確度表現などの追加・脱落を検出する静的チェックです。

### 作者プロファイル生成

```bash
python scripts/profile_author.py samples/*.md --output author-profile.json
```

形態素解析器を使わず、文長、段落長、語尾、接続表現、一人称、記号、Markdown構造などを集計します。出力は編集仕様ではなく、モデルがサンプルを読む際の補助資料です。
読者、目的、中心問い、概念的骨格、抽象化の境界、証拠の見せ方といった意味的な説明戦略は推定しません。`document` モードでは、[ソフトウェア解説](references/software-exposition.md) にある説明プロファイルを別に作ります。
対象読者が初心者の場合は、さらに [初心者向け技術説明プロファイル](references/beginner-explanation-profile.md) を使い、既知の足場、最小ケース、正確さへ戻す地点、図解の可用性、詳細の予算を決めます。
完成物が順序付きの実行案内、原因の切り分け、複数候補の選定である場合は、対応する目的プロファイルを重ねます。目的プロファイルは、場面、読者、作者の声を置き換えません。

### パッケージ検証

```bash
python scripts/validate_package.py .
```

必須ファイル、frontmatter、`agents/openai.yaml`、相対参照、SKILL.mdの行数などを確認します。

### テスト

```bash
python -m unittest discover -s tests -v
```

## 既定値

- 保真優先
- 日本語
- rewriteモード
- 場面に応じたminimalまたはbounded編集
- 作者サンプルがあれば優先
- 詳細な編集過程は要求された場合だけ表示

`document` モードは、資料化または技術説明を明示的に求められたときだけ選びます。文書化を求めないコードやログだけの入力には自動適用しません。
初心者向け技術説明プロファイルは新しいモードではなく、`document`、`rewrite`、`edit` で対象読者が初心者の場合に選ぶ説明方針です。
ガイド付きチュートリアル、トラブルシューティング、比較・選定も新しいモードや場面ではなく、依頼の主目的に応じて重ねる目的プロファイルです。既定では主目的に合うものを一つだけ選びます。
なんJスレッド風は、明示指定時だけ重ねる文体・出力形式プロファイルです。初心者向け説明や比較などと組み合わせても、元資料の事実と根拠の範囲を保ちます。

## 現時点の限界

- 固有表現と意味関係の完全な静的検証は行いません
- 作者プロファイルは形態素解析なしの軽量集計です
- 作者プロファイルは、意味的な説明戦略や資料の根拠段階を推定しません
- ソースの存在だけでは、到達可能な振る舞い、テスト結果、性能、実行中または利用者に見える運用を証明できません
- 説明構造や作者の声のサンプルは、対象のドメイン事実を供給しません
- 初心者向けプロファイルは、存在しない図や操作UIを生成済みとして扱わず、比喩だけで技術的な正しさを保証しません
- ガイド付きチュートリアルプロファイルは、資料にない操作、出力、失敗分岐、完了状態を補わず、初見読者による通し実行を自動では証明しません
- トラブルシューティングプロファイルは、観察されていない原因、権限、修正結果を補わず、設定確認だけで実環境の復旧を証明しません
- 比較・選定プロファイルは、資料にない優先順位、重み、点数、費用、候補事実、承認状態を補わず、専門家や最終決定者を代替しません
- 評価ケースはモデル横断の自動採点器ではなく、回帰試験用の仕様です
- 「人間が書いたか」「AIが書いたか」は判定しません
