# ガイド付きチュートリアルプロファイル

この参照資料は、読者が資料に支えられた操作を順に実行し、自分で途中状態と完了状態を確認できるチュートリアル、クイックスタート、ハンズオンを作るときに使う。
読みやすい手順書を、実行済みの成功談、存在しない画面、推測した出力、または権限のない操作へ変えない。

このプロファイルは、新しい処理モード、場面、読者像ではない。
主に `document`、`rewrite`、`edit` へ重ねる目的プロファイルである。
初心者向け説明プロファイルが読者の前提と概念の導入を決めるのに対し、このプロファイルは開始状態、操作、観察、失敗分岐、完了条件を決める。

## 適用条件

次の条件を満たす場合に選ぶ。

- ユーザーがチュートリアル、クイックスタート、ハンズオン、導入手順、最初の一回を案内する文書を求めている。
- 読者が到達する作業目標を定められる。
- 開始条件と、順序を持つ操作を根拠資料から抽出できる。
- 少なくとも主要な操作について、読者が照合できる観察または確認条件がある。

次の場合は自動適用しない。

- 概念説明、設計判断、APIリファレンス、仕様一覧だけを求めている。
- 症状から原因を切り分けることが中心である。この場合は [トラブルシューティングプロファイル](troubleshooting-profile.md) を使う。
- 操作順、環境、版、結果の確認方法が資料から定まらない。
- 高リスクな本番操作について、影響範囲、停止点、確認方法、復旧条件が不足している。
- 複数の実行経路から一つを選ぶ根拠がなく、選択によって結果が変わる。

材料が不足している場合は、もっともらしい通し手順を作らず、構成案、欠けている前提、必要な確認、利用できる別の資料を返す。

## 実行権限と証拠の境界

手順を書くことと、その手順を実行することは別である。
ユーザーが文書化だけを依頼した場合、外部公開、課金、アカウント作成、秘密情報の入力、削除、本番反映、再起動、設定変更を実行しない。

資料にコマンドや操作があっても、実行結果がなければ、次のように書き分ける。

- 手順として示す: 「`reportctl check` を実行します」
- 条件つきの確認: 「終了コードが0なら、検査はこの条件で成功しています」
- 実行記録がある: 「提供された実行記録では、終了コード0を確認しています」
- 禁止: 「検査に成功しました」と実行済みへ変える

命令形、未来形、条件形は手順を案内できるが、実行済みの証拠にはならない。
「完了」「確認できた」「準備が整った」は、直前に照合可能な条件がある場合だけ使う。

## 適用前に決める目的プロファイル

必要な項目だけを短く決める。
内部設計に使い、ユーザーが求めない限り表そのものは出力しない。

| 項目 | 決めること |
| --- | --- |
| 到達点 | 読者が最後に作成、実行、確認できるもの |
| 開始状態 | 必要な知識、環境、版、アカウント、ファイル、現在状態 |
| 対応経路 | 今回案内する一つの再現可能な経路と、対象外の経路 |
| 前提と依存 | ツール、権限、ネットワーク、入力データ、互換条件 |
| 秘密情報境界 | 実値を記さない資格情報、プレースホルダー、保存・開示してよい範囲 |
| 手順単位 | 一回の操作と、それが必要な理由、次に渡す状態 |
| 観察点 | 画面、出力、生成物、終了状態、実行中状態など、実際に照合できるもの |
| 失敗分岐 | 資料にある既知の症状、対処、再開地点と、未知の失敗の扱い |
| 影響と停止点 | 外部送信、費用、削除、本番変更などの前で止める地点 |
| 完了条件 | 最終操作ではなく、到達点を確認する合格条件 |
| 後始末と復旧 | 一時資源、元へ戻す方法、完全には戻らない要素 |
| 次の段階 | 応用、理論、リファレンス、別環境を主経路の外へ送る先 |

読者の開始状態と資料の前提が合わない場合は、本文を長くして取り繕わない。
準備編を分けるか、前提資料へ戻す。

## 組み立て方

次の型から、依頼と資料に合うものを選ぶ。
すべてのチュートリアルを同じ節数へ揃えない。

### 最短のクイックスタート

一つの主要経路を短時間で試す場合に向く。

```text
到達点
  -> 最小の前提
  -> 一つの設定または操作
  -> すぐ見える結果
  -> 最終確認
  -> 次に読む詳細
```

代替手段、背景理論、網羅的なオプションは主経路へ混ぜず、補足またはリファレンスへ送る。

### 確認を繰り返すハンズオン

複数の状態変化を積み上げる場合に向く。

```text
開始状態の確認
  -> 操作1 -> 観察1
  -> 操作2 -> 観察2
  -> 操作3 -> 観察3
  -> 到達点の検証
```

前の観察結果を、次の手順の開始条件として扱う。
観察できなかった場合に先へ進ませず、資料にある再開地点または確認先へ分岐する。

### 準備と最初の成果を分ける

環境構築が長い場合に向く。

```text
今回作るもの
  -> 準備だけの区画
  -> 準備完了の確認
  -> 最小の実装または操作
  -> 利用者に近い確認
```

依存先が古い、提供終了、または現在の環境で再現できない場合、警告を添えて古い主経路を続行しない。
更新された経路または追加資料が必要だと示す。

### 影響を伴う手順

外部公開、費用、秘密情報、実データ、削除、運用環境への反映を含む場合に向く。

```text
影響と対象
  -> 変更前の保存または確認
  -> 明示的な停止点
  -> 認可された操作
  -> 実環境での確認
  -> 復旧または不可逆境界
```

文書上の滑らかさより、影響、権限、回復可能性を優先する。
このプロファイルだけで、新しい操作権限を作らない。

## 一つの手順の契約

各手順は、必要な要素だけを次の順で持つ。

1. **目的**：この操作が何を次の状態へ進めるか。
2. **操作**：読者が実際に行うコマンド、入力、選択。
3. **観察**：資料に支えられた画面、出力、生成物、状態。
4. **判定**：どの条件なら進み、どの条件なら止まるか。
5. **分岐**：既知の失敗だけを、対応する操作の近くへ置く。
6. **再開地点**：対処後にどこから戻るか。

操作の理由が明らかで、誤操作の可能性が低い場合は、目的説明を省いてよい。
逆に、順序、権限、データ変更、秘密情報に関わる場合は、省略しない。

## コマンド、コード、画面、秘密情報

- コマンド、コード、URL、パス、UIラベル、数値、版、エラー文を正確に保つ。
- コマンドと、その出力例または実行結果を視覚的に分ける。
- 出力例は例であることを示し、実行記録と混同しない。
- 実際に提供しない画面、画像、ボタン、クリック、アニメーションを参照しない。
- UIラベルが資料にない場合、一般的なラベルを推測して操作させない。
- トークン、パスワード、個人情報、実データを例示のために作らない。資料が示すプレースホルダーを保持する。
- 複数プラットフォームの操作が異なる場合、一つのコードブロックへ混ぜず、開始時に経路を選ぶ。

## 失敗分岐

失敗分岐には、資料で確認できる範囲だけを書く。

```text
症状
  -> 確認できる条件
  -> 資料にある対処
  -> 再開地点
```

原因を切り分ける必要がある場合は、チュートリアル内で推測を増やさず、[トラブルシューティングプロファイル](troubleshooting-profile.md)へ切り替える。
未知の失敗は、必要なログ、公式FAQ、サポート、追加資料へ分岐し、原因や修正を創作しない。

## 初心者向け説明との組み合わせ

[初心者向け技術説明プロファイル](beginner-explanation-profile.md)と組み合わせる場合、役割を次のように分ける。

- 初心者向け: 何について初心者なのか、用語の導入、既知の足場、詳細の予算
- ガイド付きチュートリアル: 開始状態、操作順、観察点、失敗分岐、完了条件
- 場面プロファイル: README、公開記事、チャットなどに合う語域と構造
- 作者プロファイル: 語尾、距離感、リズム、許諾済みの声

初心者向けであっても、前提、専門識別子、版、秘密情報境界、安全条件を削除しない。
「簡単です」「誰でもできます」と難度を決めつけない。

## 禁止する近道

- 操作が書かれていることを、実行済みの証拠にする。
- 期待出力が資料にないのに、もっともらしい画面、ログ、生成物を作る。
- 「完了です」で終え、観察可能な合格条件を示さない。
- すべての背景説明、代替手段、仕様を主経路へ詰め込む。
- 失敗の原因、修正、再開地点を推測で補う。
- 対応版、依存先、プランが古いまま、警告だけを添えて再現可能とする。
- チュートリアルを、外部公開、課金、秘密情報入力、削除、本番変更の権限へ読み替える。
- 初心者向けを理由に、専門語、条件、エラー、版、安全上の注意を消す。
- 非手順文書を、見出しと番号を足しただけのチュートリアルへ変える。
- 説明構造サンプルのコード、製品事実、数値、口癖を対象へ移す。

## 完了監査

- 読者の到達点と開始状態を、資料の範囲で定めたか。
- 一つの主要経路を選べる根拠があり、対象外の経路を隠していないか。
- 各手順の操作、観察、判定、再開地点を追えるか。
- コマンド、コード、識別子、数値、版、順序依存を保持したか。
- 期待結果、出力例、実行記録を区別したか。
- 「成功」「完了」が、実行証拠または明示された条件に結び付いているか。
- 既知の失敗だけを扱い、未知の原因や対処を補っていないか。
- 外部作用、費用、秘密情報、削除、本番変更の前に、影響と停止点があるか。
- 初心者向けと組み合わせても、前提、専門語、安全条件を削除していないか。
- 非手順文書を無理にチュートリアル化していないか。
- 後始末、復旧、または完全には戻らない要素を資料の範囲で示したか。
- 初見読者による通し実行がない場合、再現性を検証済みと主張していないか。
