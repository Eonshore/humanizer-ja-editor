# 比較・選定プロファイル

この参照資料は、二つ以上の製品、技術、方式、サービス、実装案、または現状維持案を、利用条件と根拠に沿って比較し、条件つきの判断材料を作るときに使う。
比較文を、根拠のない総合順位、未知を0点とする採点、異なる条件の測定を並べた勝者、または購入・導入済みの決定へ変えない。

このプロファイルは、新しい処理モードや場面ではない。
主に `document`、`rewrite`、`edit`へ重ねる目的プロファイルであり、最終決定、購入、契約、導入、設定変更、公開の権限を作らない。

## 適用条件

次の場合に選ぶ。

- 複数の候補または現状維持案から選ぶための材料を作る。
- 利用場面ごとの使い分け、導入、移行、採用、購入前の比較を行う。
- 必須条件、共通評価軸、証拠の確かさ、トレードオフを分ける必要がある。
- 結論が用途、優先順位、未検証事項によって変わりうる。

次の場合は自動適用しない。

- 単一候補の説明またはレビュー。
- 判断を求めない仕様差分、一覧、文章表現だけのA/B比較。
- 候補の版、プラン、環境、測定条件が異なり、比較可能性そのものが成立していない。
- 医療、法務、金融などで、専門家または権限者の判断をこのプロファイルだけで代替する。

「AとBはどちらがよいか」だけでは、用途によって結論が変わる場合がある。
重要な不足があれば確認し、軽微な不足なら狭い仮定を明示した暫定比較にする。
情報不足を埋めて一般的な最強を作らない。

## 判断権限の境界

比較、推奨、決定、実行を分ける。

- **比較**：共通条件で候補の証拠、利点、代償、未知を整理する。
- **推奨**：明示された条件のもとで、どの候補が適するかを示す。
- **決定**：権限を持つ主体が、費用、リスク、未検証事項を引き受けて選ぶ。
- **実行**：購入、契約、導入、移行、設定、外部送信を行う。

比較依頼を、その後の決定または実行の許可へ読み替えない。
推奨文に最終決定者、承認状態、未実施の次の行動を正確に残す。

## 適用前に決める目的プロファイル

必要な項目だけを短く決める。

| 項目 | 決めること |
| --- | --- |
| 判断課題 | 何を選び、どの行動を支える比較か |
| 利用者と場面 | 誰が、どの環境、規模、頻度、期間で使うか |
| 候補 | 比較する版、プラン、構成と、現状維持案を含むか |
| 必須条件 | 満たさなければ選べない条件、禁止条件、証明が必要な条件 |
| 評価軸 | 全候補へ同じ意味と条件で適用する軸 |
| 優先順位 | ユーザー、組織方針、合意済み基準が示す重みまたは順序 |
| 証拠 | 出典、観察、測定、対象版、日付、環境、適用範囲、確度 |
| 比較可能性 | 版、入力、環境、測定方法、期間を揃えられるか |
| ライフサイクル | 導入、移行、運用、更新、撤退、再評価の負担とリスク |
| 未知 | 証拠がない項目、比較不能な項目、必要な追加検証 |
| 推奨形式 | 一候補、用途別、複数候補、推奨不能のどれが妥当か |
| 決定主体 | 誰が最終判断し、どの承認または検証が残るか |

## 必須条件を先に扱う

加点評価より先に、必須条件を確認する。
各候補と条件の組み合わせを、次のどれかへ分類する。

- `met`: 満たす証拠がある。
- `not_met`: 満たさない証拠がある。
- `unknown`: 判断に必要な証拠がない。
- `not_applicable`: その候補には適用しない。

`unknown`を`not_met`、0点、劣位へ変換しない。
ただし、認証の提出、権利確認、互換性証明など「証明できること自体」が必須なら、証拠不足を性能上の劣位ではなく、選定を進められない検証ブロッカーとして示す。

必須条件を満たさない候補を、無関係な加点の合計で復活させない。

## 共通評価軸

案件に必要な軸だけを選び、全候補へ同じ定義で適用する。
次は候補であり、固定チェックリストではない。

- 主要な利用目的への適合
- 必須機能と品質条件
- 導入、学習、移行の負担
- 運用、監視、障害対応、必要スキル、サポート
- セキュリティ、プライバシー、権利、ガバナンス
- 既存環境との統合、互換性、データ形式
- 導入費用と総保有コスト
- 更新、版変更、提供継続のリスク
- データ、設定、成果物の可搬性
- ロックイン、撤退時間、撤退費用、代替経路
- 証拠の直接性、適用条件、鮮度
- 未検証事項と次の検証方法

一方の候補を有利にするため、評価後に軸を追加しない。
似た軸を重ねて同じ長所を二重加点しない。

## 証拠表

各セルを「良い」「弱い」の一語で済ませず、必要な範囲で次を対応付ける。

| 項目 | 内容 |
| --- | --- |
| 結論 | この軸について言える範囲 |
| 証拠種別 | 公式仕様、ソース、再現、測定、運用観測、第三者評価など |
| 出典または観察方法 | どこから確認したか |
| 条件 | 版、プラン、入力、環境、期間、測定方法 |
| 適用範囲 | どの利用場面まで言えるか |
| 制約 | 例外、対象外、相反する資料 |
| 確度 | 確認済み、限定的、未確認など |
| 未知 | 次に必要な資料または検証 |

異なる版、プラン、環境、入力、期間、測定方法の結果は、同条件の差として順位付けしない。
参考情報または比較不能として示す。

ベンダーの自己申告は、ベンダーが述べている事実として帰属表示する。
独立した再現または観察がない場合、独立確認済みへ強めない。

## 数値評価と重み

数値の点数と重みは既定では使わない。
使用できるのは、次のいずれかの場合である。

- ユーザーが優先順位または重みを明示した。
- 組織の既存方針、調達基準、合意済み評価基準がある。
- 利害関係者との明示的な合意過程から得た。

重みの出所を残し、勝手に正規化、追加、変更しない。
根拠がない場合は、必須条件、優越関係、用途別の比較で結論を作る。

数値を使う場合も、次を確認する。

- 尺度の意味が候補間で同じか。
- 未知を0点としていないか。
- 重複軸を二重加点していないか。
- 重みを変えると推奨が反転するか。
- 小さな点差が、証拠の不確実性より大きいか。

根拠のない「機能30%、価格20%」を作らない。

## ライフサイクルで見る

導入時の魅力だけで終わらせず、資料にある範囲で次を確認する。

```text
導入前: 学習、契約、検証、移行準備
  -> 導入時: 実装、データ移行、受け入れ条件
  -> 運用時: 監視、障害対応、品質維持、費用変動
  -> 更新時: 互換性、API、モデル、契約の変更
  -> 撤退時: データ出力、代替経路、切替時間・費用、rollback
  -> 再評価: 要件、価格、品質、提供状況、リスクが変わる条件
```

可搬性が低い候補を常に失格としない。
便益、移行負担、撤退可能性を同じ判断単位で扱う。

## 組み立て方

### 必須条件で絞ってから比較する

```text
判断課題
  -> 必須条件
  -> 残った候補
  -> 共通軸の証拠
  -> トレードオフ
  -> 条件つき推奨
```

### 用途ごとに結論を分ける

```text
共通の判断文脈
  -> 用途Xの優先条件 -> 候補A
  -> 用途Yの優先条件 -> 候補B
  -> 共通する未知と再評価条件
```

### 証拠不足を正式な結論にする

```text
判断に必要な必須証拠
  -> 現在ある証拠
  -> 不足または比較不能
  -> 推奨不能の理由
  -> 結論を変える追加検証
```

推奨不能は失敗した文章ではない。
比較に必要な証拠が足りない場合の正しい結果である。

## 推奨の形式

結論は、資料と条件に応じて次から選ぶ。

- 条件付きでAを推奨する。
- 条件付きでBを推奨する。
- 用途XではA、用途YではBを推奨する。
- 有力候補は複数で、追加検証後に決定する。
- 必須証拠が不足しているため推奨できない。
- 必須条件を満たす候補がない。

結論には、必要な範囲で次を添える。

- 決定的だった条件と評価軸
- 推奨が成立する条件
- 推奨の強さ
- 証拠の確かさ
- 明示的に劣位だった事実
- 未知のまま残った事実
- 結論が反転する条件
- 次の検証
- 最終決定者と未承認状態

証拠の確かさと推奨の強さを同じ尺度へ潰さない。
限定的な証拠でも、必須条件と影響の非対称性によって強い行動判断が必要な場合がある。
逆に、個別の証拠が強くても、利用目的が不明なら総合推奨は弱い。

## 初心者向け説明との組み合わせ

[初心者向け技術説明プロファイル](beginner-explanation-profile.md)と組み合わせる場合、初心者向けプロファイルは用語、前提、最小ケースを橋渡しし、比較・選定プロファイルは判断文脈、必須条件、共通軸、未知、結論を管理する。

専門語をやさしく導入しても、版、プラン、測定条件、証拠の確度、費用、安全条件を消さない。
初心者向けを理由に、利用者の優先順位を勝手に決めない。

## 禁止する近道

- 判断目的と利用条件なしに一般的な「最強」を決める。
- 候補ごとに異なる版、プラン、入力、環境、期間、測定方法を同条件の差として並べる。
- 一方だけベンダー資料、他方だけ独立試験を使い、同じ確度の証拠とする。
- `unknown`を`not_met`、0点、劣位へ変換する。
- 必須条件と加点条件を混ぜる。
- 根拠のない数値重み、総合点、星、順位を作る。
- 似た評価軸で同じ長所を二重加点する。
- 推奨の強さと証拠の確かさを一つの評価語へ潰す。
- 導入時の利点だけを書き、運用、更新、撤退を省く。
- 比較を購入、契約、導入、設定変更、公開の許可へ読み替える。
- 比較結果を、意思決定者が承認済みの決定として書く。
- 説明構造サンプルの固有基準、点数、候補順位、製品事実、口癖を対象へ移す。

## 完了監査

- 何を、誰が、どの利用場面で決める比較かを示したか。
- 候補の版、プラン、環境、確認日、最終決定者を必要な範囲で定めたか。
- 必須条件を加点条件より先に扱ったか。
- `met`、`not_met`、`unknown`、`not_applicable`を混同していないか。
- 全候補へ同じ評価軸と比較条件を適用したか。
- 異なる条件の証拠を、直接順位へ変えていないか。
- ベンダー主張と独立した観察を区別したか。
- 数値重みの出所があり、結論の感度を確認したか。
- 導入、移行、運用、更新、撤退、再評価のうち必要な時間軸を扱ったか。
- 推奨の強さと証拠の確かさを分けたか。
- 未知、比較不能、推奨不能を正規の結果として残したか。
- 結論が成立する条件、反転する条件、次の検証を示したか。
- 比較、推奨、決定、実行の権限境界を守ったか。
- 入力にない順位、重み、点数、費用、候補事実、承認状態を追加していないか。
