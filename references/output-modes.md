# 出力モード

## rewrite

既定モード。既存文の編集を扱う。短い会話応答の作成を明示的に求められた場合は、共有済みの文脈から完成文を返し、存在しない原文や編集差分を作らない。

### 貼り付け文章

原則として完成版を一つ返す。ユーザーが理由を求めた場合、または変更が大きい場合だけ、後に短い変更要約を付ける。

```text
[完成版]

変更要約
- 空の前置きを削除
- 確度表現と数値は維持
```

複数案を自動で出さない。選択肢が必要な場合はユーザーの明示指示に従う。

### 変更できない問題がある場合

出典不足、曖昧な数量関係、主体不明など、文章編集だけで安全に解決できない箇所は短く明示する。

```text
要確認: 「40%改善」の対象と比較基準が原文から特定できません。
```

推測で埋めない。

## annotation

全文を書き換えない。重要度の高い問題を1〜5件に絞る。

各項目は次の形式を使う。

```text
問題: 無源引用
該当: 「複数の研究が示すように」
理由: 後続の数値が出典に依存しています。
推奨: 出典を補うか、論断ごと削除します。
改写推奨: はい
```

次の場合は「改写推奨: いいえ」とする。

- 技術用語やコードを誤検出している
- 箇条書きが機能的である
- 学術上必要な限定である
- 作者サンプルと一致する意図的な表現である
- 小説上の文体効果である

材料不足の場合は次を示す。

- 空の表現を削ると何が残るか
- 不足しているのが事実、例、根拠、判断のどれか
- 文章を長く保つために架空情報を追加できないこと

## edit

ファイルを直接編集する。

手順:

1. 対象ファイルと範囲を読む
2. コード、表、引用、構造化データを保護する
3. 自然な箇所を残し、問題箇所だけ編集する
4. 編集後に差分を読む
5. `protect_audit.py` を使える場合は実行する
6. 変更内容と要確認点を短く報告する

報告例:

```text
README.mdの導入部を編集しました。
- 宣伝的な評価語を削除
- 機能説明とインストール手順は維持
- バージョン、コマンド、リンク先の変更なし
```

大きなファイルでも、ユーザーが範囲を指定している場合は勝手に全文を再編集しない。

## document

提供された情報から説明、案内、技術・設計文書を作る。
一般の案内は、読者、行動、期限、条件、例外を資料の範囲で整理し、完成文を返す。ソフトウェア用の根拠段階や説明プロファイルは要求しない。

以下の資料分類と説明プロファイルは、リポジトリ、コード、テスト、設計資料、ベンチマーク出力、ログから技術や設計を説明する場合に使う。
既存の文章を整える `rewrite` とは異なり、複数資料の説明順を組み替えてよい。
ただし、資料から読み取れない動作、性能、運用実績を補うことはできない。

作成前に、次を分ける。

1. 根拠・事実資料、作者の声のサンプル、説明構造のサンプル
2. 読者、目的、中心問い、抽象化の境界を記した説明プロファイル
3. 設計主張、ソースの存在、到達可能な経路、テストまたは再現、測定、実行観測の根拠段階
4. 必要な場合だけ、分野の初心者向け説明、日本語の読みやすさ、チュートリアル・トラブルシューティング・比較選定の目的プロファイル。分野知識と日本語力は別々に判断する

詳細は [ソフトウェア解説](software-exposition.md) を読む。

### 既定の出力

目的と根拠が十分にある場合は、完成文を一つ返す。
本文は問題または問いから始め、動作原理、仕組み、条件、証拠、限界を読者の目的に合わせて並べる。
これは固定テンプレートではなく、設計解説、調査報告、公開記事、APIリファレンスなど完成物に合わせて変える。

必要な場合だけ、本文の前後へ次を短く付ける。

- 仮定：資料から安全に置いた暫定の読者または目的
- 根拠の範囲：主張が設計資料、ソース、テスト、測定、実行観測のどこまでに支えられるか
- 要確認：完成文へ入れられない不足資料または未検証条件

根拠表、識別子の一覧、コード断片、詳細な呼び出し経路は、読者の判断や再現に必要なときだけ本文外へ置く。
通常の解説では、ディレクトリ順、モジュール順、関数の呼び出し順に本文を進めない。

### 資料不足時の出力

読者または目的が不明でも、技術的な主張の範囲を変えない狭い仮定を置ける場合は、仮定をラベル付けして完成文を作る。

例:

```text
仮定: 対象読者は、このリポジトリを保守する開発者です。
```

目的、公開範囲、対象読者によって結論や構成が実質的に変わる場合、または主張を支える資料が不足する場合は、完成した説明を捏造しない。
代わりに、概念的なアウトライン、現時点で言えること、根拠の不足箇所、必要な資料を返す。

```text
アウトライン
1. 確認できたソースの構成
2. 目的として文書に書かれていること
3. 実行、テスト、測定について不足している証拠

要確認
- 実行結果または再現手順
- 想定読者と、この文書で支える判断
```

### API・参照文書の例外

ユーザーがAPIリファレンス、モジュール参照、呼び出し経路、デバッグ手順を明示的に求める場合は、公開API、識別子、構成、呼び出し順を主構造にしてよい。
それでも、内部実装の存在から実行済みの振る舞い、性能、利用者に見える状態を主張しない。

## 明示的ななんJスレッド風の出力

[なんJスレッド風プロファイル](nanj-thread-profile.md) が指定された場合は、選択済みのモードへ口調とレス形式を重ねる。
`rewrite` と `document` は完成スレを一つ返し、`edit` は指定されたファイル範囲だけをスレ化する。`annotation` は通常どおり問題点だけを返す。
創作だと分かる表示、レス番号、名無し表記、必要なアンカー、発言の長短を使う。既定で各レスの後に編集解説や根拠台帳を付けない。
元資料の条件や確度、引用、出典は、対応する説明レスへ残す。「口調だけ」の指定ならレス形式へ変えない。

## 長文の扱い

### minimal / in-place要求

ユーザーが「文数を変えない」「一文も削除しない」「行構造を保つ」と指定した場合:

- 文内の語句だけ変更する
- 文の結合、段落移動、全文圧縮をしない
- 空文は残し、必要なら要確認として報告する

### bounded

空の一文は削除できる。実質情報、引用、条件、確度、責任、段落順を保つ。

### structural

構成変更を求められた場合だけ行う。変更要約に、移動・統合・削除した構造を記す。

## 出力しないもの

- 隠れた推論過程
- 「AIらしさスコア」や作者性の断定
- ユーザーが求めていない大量の診断
- 書き換え前後を装飾した冗長な比較
- 元文にない参考文献や補足例
- `document` モードで、作者の声や説明構造のサンプルから持ち込んだ対象外の事実、実装、性能、到達状態
