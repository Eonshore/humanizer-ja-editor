# トラブルシューティングプロファイル

この参照資料は、不具合、障害、設定と実行状態の食い違い、導入失敗、断続的な症状、性能劣化、環境差について、症状、観察、仮説、原因確度、対応、再検証を分けて説明するときに使う。
自然な障害説明を、未確認の根本原因、権限のない修正、設定だけで証明した復旧、または回避策を根治とする報告へ変えない。

このプロファイルは、新しい処理モードや場面ではない。
`annotation`、`rewrite`、`edit`、`document`へ重ねる目的プロファイルであり、依頼された権限境界を広げない。

## 適用条件

次の場合に選ぶ。

- バグ報告、障害調査、原因の切り分け、導入失敗、環境差、修正後の報告を作る。
- 期待した状態と観察された状態の差を扱う。
- 複数の原因候補を、ログ、状態、再現、検査で区別する必要がある。
- 回避策、修正、再検証、rollbackの境界を説明する必要がある。

次の場合は自動適用しない。

- 原因調査を伴わない既知エラーへの短い回答。
- 順序どおりの操作説明が中心である。この場合は [ガイド付きチュートリアルプロファイル](guided-tutorial-profile.md) を使う。
- 一般概念の説明、表記修正、APIリファレンスだけの依頼。
- セキュリティ・フォレンジック、証拠保全、データ破壊、不可逆移行など、専用の安全手順が優先される作業。

短い既知エラーに、このプロファイルの全区画を押し付けない。
逆に、期待、実際、対象環境のどれかが欠け、原因判断へ影響する場合は、暫定診断または不足資料として示す。

## 依頼モードと権限境界

最初に、依頼が次のどこまでを含むかを分ける。

| 依頼 | できること | できないこと |
| --- | --- | --- |
| 診断のみ | 症状整理、観察、仮説、切り分け、原因確度の説明 | 設定変更、再起動、削除、外部送信、修正実行 |
| 修正提案まで | 診断に加え、最小修正、影響、検証、rollback案を示す | 提案を実施済みまたは承認済みと書くこと |
| 変更実行を含む | 認可された対象だけを変更し、実動作を再検証する | 隣接領域、管理者操作、外部作用、不可逆変更へ範囲を広げること |

診断依頼を、修正権限として扱わない。
変更主体、承認主体、確認主体が異なる場合、その役割を文章から消さない。

## 適用前に決める目的プロファイル

必要な項目だけを短く決める。

| 項目 | 決めること |
| --- | --- |
| 依頼範囲 | 診断、提案、実行、報告のどこまでか |
| 期待状態 | 誰から見て、何が、どの条件で起きるべきか |
| 観察症状 | 実際の動作、影響、発生時刻、頻度、対象環境 |
| 比較対象 | 正常環境、最後に動いた時点、発生しない条件 |
| 観察資料 | ログ、設定、プロセス、終了状態、測定、利用者向け動作と取得時点 |
| 仮説 | 観察と整合する候補、反証条件、まだ説明できない点 |
| 切り分け | 仮説間を区別する検査、危険性、必要権限、結果の読み方 |
| 原因確度 | 確認済み、有力、可能性あり、未特定のどこか |
| 暫定対応 | 影響を抑える回避策、その期限、制約、副作用、解除条件 |
| 最小修正 | 仮説に対応する最小対象、変更しない隣接領域 |
| 再検証 | 元の症状、実行状態、利用者向け動作、最小回帰の確認 |
| Rollback | 対象、既知の正常状態、発動条件、実施主体、復元後の確認 |

## 症状、観察、仮説、原因、対応を分ける

同じ文の中で、観察と推測を原因へまとめない。

```text
症状: 利用者画面で保存操作が終了しない。
観察: 20:14のログにtimeoutが記録されている。
仮説: 保存先への接続遅延が関係している可能性がある。
原因判断: 接続遅延が原因かは未確認である。
次の切り分け: 同時刻の接続状態と、正常環境との差を確認する。
```

禁止例は次のとおりである。

```text
接続遅延が原因で保存に失敗しました。
```

ログの同時発生だけでは、因果を確定できない。

## 証拠段階

設定、診断上の実行可能性、現在の実行状態、利用者に見える動作を別々に扱う。

| 段階 | 支えられる言い方 | それだけでは言えないこと |
| --- | --- | --- |
| 設定 | 「設定値は有効になっている」 | プロセスが読み込んだ、現在動いている、利用者が使える |
| 静的な到達可能性 | 「この条件では処理経路が存在する」 | 実際にその経路が実行された |
| プロセス・サービス状態 | 「この時点でプロセスが起動中である」 | 正しい入力へ応答する、利用者に機能が見える |
| 再現・テスト | 「この条件で症状または修正を再現した」 | 未検証条件、継続運用、全利用者での解決 |
| 利用者向け確認 | 「この時点の実環境で元の操作が成功した」 | 再起動後の永続性、別環境、長期安定性 |

観察には、可能な範囲で取得時点、環境、対象、観察方法を残す。
古いログや別環境の結果を、現在の状態へ無条件に移さない。

## 仮説と切り分け

各仮説について、次を対応付ける。

```text
仮説
  -> 支える観察
  -> 反証になり得る観察
  -> 仮説間を区別する検査
  -> 検査の副作用と必要権限
  -> 結果から言える範囲
```

- 最近の変更と症状が同時に発生しても、機序または識別的な検査がなければ相関にとどめる。
- 複数の仮説へ同じ結果を返す検査では、原因確度を上げない。
- 陰性結果も、除外できた候補と除外できない候補を分ける証拠として残す。
- 再現が危険または不可能な場合、確定を装わず、最も整合する要因と未確認範囲を示す。
- 原因調査のために秘密情報、個人情報、運用データを不必要に開示しない。

## 原因確度

数値の確率を推測せず、根拠に応じて次のように表現する。

- **確認済み**：再現、反証、修正前後の検査など、原因判断を直接支える証拠がある。
- **有力**：複数の観察と整合し、主要な別仮説が狭まっているが、直接確認が不足している。
- **可能性あり**：症状と整合するが、識別的な検査がまだない。
- **未特定**：資料から候補を安全に絞れない。

直接原因、寄与要因、背景条件を分ける。
必ず一つの「根本原因」を作る必要はない。

## 組み立て方

### 短い既知症状の参照

既知のエラーメッセージと確認済み対処がある場合に向く。

```text
症状またはメッセージ
  -> 発生条件
  -> 確認方法
  -> 回避策または修正
  -> 再確認
```

### 探索的な診断

原因が未特定で、複数仮説を分ける場合に向く。

```text
期待と実際
  -> 観察済みの事実
  -> 仮説
  -> 識別する検査
  -> 現在の原因確度
  -> 次の安全な確認
```

### 影響を抑えてから調査する

利用者影響が続く障害に向く。

```text
影響と現在状態
  -> 暫定対応
  -> 証拠保全
  -> 原因調査
  -> 最小修正
  -> 実環境での再検証
  -> 恒久対応
```

緊急時には原因確定より復旧を先行できるが、回避策を根治と書かず、残る調査を示す。

### 修正後の報告

変更が実施済みで、証拠が揃っている場合に向く。

```text
変更対象
  -> 変更前の証拠
  -> 実施した変更
  -> 元の症状の再検証
  -> 隣接機能の最小回帰
  -> 再起動または新規実行での確認
  -> 残るリスクとrollback
```

## 回避策、修正、恒久対応

三つを同義にしない。

- **回避策**：影響を一時的に減らす。制約、副作用、有効期限、解除条件を付ける。
- **修正**：特定した原因または有力仮説へ対応する最小変更。対象と非対象を明示する。
- **恒久対応**：再発防止、監視、テスト、運用改善、横展開。単一の修正成功から自動的に保証しない。

回避策で症状が消えても、原因を直接検証していなければ、根治とは書かない。

## 再検証とrollback

修正の完了条件は、設定保存、コマンド成功、デプロイ完了だけではない。

1. 元の症状を、同じ条件または妥当な再現条件で確認する。
2. 対象プロセスまたはサービスの実行状態を確認する。
3. 可能なら、利用者が行う操作に近い入口から確認する。
4. 変更が壊し得る隣接機能の最小回帰を確認する。
5. 必要なら、新しいプロセス、再起動、再ログイン後の永続性を確認する。

確認できない段階は `未検証` とし、必要な次の検査を示す。

rollbackについて、次を事前に定める。

- 戻す対象と既知の正常状態
- 発動条件
- 実施主体と必要権限
- 戻した後に確認する実動作
- 完全には戻らないデータ、外部副作用、移行状態

部分復元しかできない場合、rollback可能とだけ書かない。

## 禁止する近道

- 利用者が書いた原因推測を、確認済みの根本原因へ変える。
- 最近の変更と症状の相関を、機序や識別的な検査なしで因果とする。
- 設定が有効であることを、実行中または利用可能な証拠にする。
- 診断依頼を、設定変更、再起動、削除、外部送信の権限に変える。
- 回避策で症状が消えたことを、原因確定または恒久解決とする。
- 一つの原因へ収束するために、寄与要因や未確認事項を削る。
- コマンド成功や設定保存だけで、元の症状が解決したとする。
- 実環境の再検証がない状態を、完了または受入済みと書く。
- 完全には戻らない変更を、rollback可能とだけ表現する。
- すべての短い問い合わせを、長い障害報告書へ変える。
- 説明構造サンプルの製品、原因、コマンド、障害事実、口癖を対象へ移す。

## 完了監査

- 依頼が診断、提案、実行、報告のどこまでかを守ったか。
- 期待状態、実際の症状、対象環境、観察時点を追えるか。
- 症状、観察、仮説、原因判断、対応を分けたか。
- 設定、到達可能性、実行状態、利用者向け動作を別の証拠として扱ったか。
- 相関を原因へ昇格させていないか。
- 各検査が仮説間を区別し、必要権限と副作用を考慮しているか。
- 原因確度が証拠の強さを越えていないか。
- 回避策、最小修正、恒久対応を区別したか。
- 修正を実施した場合、元の症状、実行状態、利用者向け動作、最小回帰を確認したか。
- 確認できない段階を `未検証` として残したか。
- rollback対象、発動条件、主体、復元後の確認、不可逆部分を示したか。
- 入力にない原因、数値、コマンド、権限、成功結果を追加していないか。
