# 初心者向け技術説明プロファイル

この参照資料は、技術分野へ初めて入る読者に向けて、概念、仕組み、条件、根拠、限界を説明するときに使う。
初心者向けの説明を、幼児語への置換、専門語の削除、著名な解説者の文体模倣、または事実を省いた比喩へ変えない。

このプロファイルは新しい処理モードや場面ではない。
ユーザーが初心者、新入門者、非専門家向けの説明を明示した場合、または完成物の読者が対象分野の用語をまだ知らないと資料から確認できる場合に、`document`、`rewrite`、`edit` の説明方針として選ぶ。

## 読者との契約

ここでいう初心者は、対象分野の語彙や慣習をまだ共有していない読者である。
理解力、判断力、一般的な経験まで不足しているとは扱わない。

- 予備知識を暗黙に要求しない。必要な前提は、本文の冒頭または必要になる直前に示す。
- 読後目標を「完全に理解する」のような抽象語にせず、説明できること、見分けられること、次に行える操作または判断で定める。
- 一度に導入する中心概念を絞る。未説明の専門語を使って別の専門語を定義しない。
- 読者を称賛、採点、子ども扱いしない。「簡単です」「誰でも分かります」と理解の難度を決めつけない。
- 口語性は距離を縮めるために使ってよいが、正確さ、検索性、責任主体、確度を弱めない。

## 適用前に追加する説明プロファイル

[ソフトウェア解説の説明プロファイル](software-exposition.md#説明プロファイル)に加えて、必要な項目だけを短く決める。
このメモは内部設計に使い、ユーザーが求めない限りそのまま出力しない。

| 項目 | 決めること |
| --- | --- |
| 初心者の範囲 | 分野全体、特定製品、数式、CLI、運用など、何について初めてなのか |
| 既知の足場 | 資料から安全に使える日常的な対象、既知の操作、最小の具体例 |
| 読後目標 | 読者が説明、識別、操作、判断できる範囲 |
| 最初の問い | 用語の定義より先に回収する、読者にとっての問題または疑問 |
| 最小ケース | 全体の仕組みを失わずに追える、資料に支えられた最小の例 |
| 正確さへ戻る地点 | 暫定的な単純化や比喩を、正式な用語、条件、仕組みへ接続する位置 |
| 図解の可用性 | 実際に図を出せるか、文章内の短い流れや表で代替するか |
| 詳細の予算 | 本文へ残す数式、コード、識別子と、注記や次段階へ送る詳細 |

読者の前提を資料から判断できない場合は、「対象分野の用語をまだ知らない読者」のような狭い仮定を明示してよい。
想定によって説明内容、公開範囲、必要な安全情報が変わる場合は、仮定で埋めずに確認する。

## 説明の組み立て方

次の型から、中心問いと資料に合うものを一つ選ぶか、必要な部分だけ組み合わせる。
全記事を同じ節数、同じ見出し、同じ対話形式へ揃えない。

### 全体から一段ずつ開く

複雑なアーキテクチャや処理系に向く。

```text
入出力を持つ一つの箱
  -> 箱の中の主要部分
  -> 今回見る一部分
  -> その部分を流れる情報
  -> 必要な正確な詳細
```

最初の全体図と後の詳細図で、同じ対象の名前や向きを変えない。
詳細を追加するたびに、それが全体のどこへ戻るかを示す。

### 素朴な案が困る条件から導く

アルゴリズム、データ構造、性能上の工夫に向く。

```text
小さく単純な場合
  -> 新しい制約
  -> 素朴な案が失敗する理由
  -> 新しい考え方
  -> 成り立つ理由
  -> 実装または利用条件
```

素朴な案を無能な案として扱わない。
どの条件までは使え、何が変わると困るのかを資料の範囲で示す。

### 混乱を観察可能な部品へ分ける

OS、ネットワーク、コンテナ、デバッグ、運用に向く。

```text
読者が混同しやすい問い
  -> 構成する最小の仕組み
  -> コマンド、ログ、状態などの観察
  -> 観察から言えること
  -> 観察だけでは言えないこと
```

コマンドやログを成功談にしない。
実行条件、権限、版、観察時点が資料にある場合は保持する。

### 効果と代償を先に置く

短い概念解説、採用判断、トレードオフのある技術に向く。

```text
何を減らす、増やす、置き換える技術か
  -> 得られる効果と失う可能性
  -> 最小の仕組み
  -> 適する条件
  -> 適さない条件または未検証範囲
```

利点だけを先に固定しない。
資料が示す代償、例外、不確実性を同じ判断単位へ置く。

## 用語、数式、コードの導入

用語は、必要性を示した後、初出時に平易な日本語と原表記を対応させる。
正式名称を消すと検索や実装が難しくなるため、言い換えだけで置き換えない。

暫定的に単純化する場合は、その範囲を示す。

```text
まずはXを「Yを保持するもの」と考えます。
実際にはZという条件もあり、後でこの点へ戻ります。
```

単純化を本文の最終定義にしない。
説明を進めるための心的モデルと、設計上の定義、実装で観察した振る舞いを区別する。

数式やコードは、それが答える問いを先に示してから出す。

- 数式では、各記号が何を表し、式の入力と出力が何かを説明する。
- コードでは、全行を逐次解説せず、公開契約、条件、結果、必要な証拠アンカーを示す。
- API、CLI、設定キーは、読者が実際に使う名前を保持する。
- 内部ヘルパーや局所変数は、中心問いに必要でなければ本文から退避する。

## 図解と比喩

図解は文章の装飾ではなく、一つの関係、流れ、比較を目で追えるようにするために使う。

- 実際に図を提示しない出力で「下図」「クリック」「スライダーを動かす」と書かない。
- 図を出せない場合は、短い文字列フロー、対応表、番号付き手順など、実際に読める形式へ置き換える。
- 一つの図で新しい概念を詰め込みすぎない。本文と図で同じ用語を使う。
- 図の直後には、読者が見るべき関係を一つ示す。図の全要素を散文で重複させない。

比喩を使う場合は、次の三点を揃える。

1. 何を理解するための比喩か。
2. 比喩の各要素が、対象の何に対応するか。
3. どこから対応しなくなるか。

比喩を証拠、定義、因果関係の代わりにしない。
資料にない固有の数字、性能、実装を、比喩を具体的に見せるために追加しない。

## 読者との対話

問いかけは、直前までの説明から自然に生じる疑問を回収する場合だけ使う。
各節を「では何でしょうか」「実は簡単です」で始める固定パターンにはしない。

- 読者が次に疑問に思う理由を、既存資料から説明できる場合に問いを置く。
- 問いを置いたら、同じ節または直後で回収する。
- 架空の読者に誤答させて、書き手を賢く見せる対話を作らない。
- 作者サンプルにない一人称の体験、感情、失敗談を追加しない。

## 禁止する近道

- 専門語を削れば初心者向けになると考える。
- 短文、疑問形、感嘆符、顔文字を増やして親しみやすさを演出する。
- 資料にない日常例、失敗談、数字、利用者像を足す。
- 一つの比喩で仕組み、性能、安全性まで説明したことにする。
- 実際には存在しない図、アニメーション、操作UIを参照する。
- 説明構造サンプルの企業、製品、実装、性能を対象へ移す。
- 「初心者には不要」という理由だけで、条件、例外、確度、安全上の注意を落とす。
- すべての記事を、問い、たとえ、三項要約、励ましの同じテンプレートへ揃える。

## 完了監査

- 読者が何について初心者なのかを、必要な範囲で定めたか。
- 中心問いと読後目標が、資料の範囲で具体的か。
- 用語の名前より先に、必要になる理由または最小の対象を示したか。
- 暫定的な単純化を、正式な用語、条件、仕組みへ戻したか。
- 数式、コード、識別子の量は、読後目標に必要な範囲か。
- 比喩には対応関係と限界があり、対象の事実を置き換えていないか。
- 実在しない図や操作を参照していないか。
- 初心者を子ども扱い、称賛、採点していないか。
- 説明構造サンプルから、口癖、企業固有情報、技術事実を持ち込んでいないか。
- 設計上の期待、ソース、テスト、測定、実行観測の根拠段階を保ったか。
- 読者が現在言えることと、次に読む、試す、確認する範囲が分かるか。
