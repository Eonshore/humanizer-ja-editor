# 概念先行のソフトウェア解説

この参照資料は、リポジトリ、コード、テスト、既存文書、ベンチマーク出力、ログなどから、技術や設計を説明する文書を作るときに使う。
対象は、コードの逐次解説ではなく、読者が問題、考え方、仕組み、適用条件、根拠、限界を判断できる説明である。

コードだけ、ログだけ、またはAPI定義だけを受け取った場合に、自動で解説文を作るための規則ではない。
ユーザーが資料化、技術説明、設計説明、概念先行の解説を明示的に求めた場合だけ `document` モードを選ぶ。

## 資料の役割を分ける

入力資料を読む前に、各資料へ役割を割り当てる。
同じ資料を複数の役割へ使う場合は、なぜ各役割に使えるかを説明プロファイルへ記す。

| 役割 | 使うもの | 決めてよいこと | 決めてはいけないこと |
| --- | --- | --- | --- |
| 根拠・事実資料 | 対象の設計資料、ソース、テスト結果、再現記録、測定結果、実行観測 | どの主張がどの根拠段階まで支えられるか | 根拠段階を越えた動作、性能、運用実績 |
| 作者の声のサンプル | 許諾済みの文章、対象と同じ用途の既存文書 | 語尾、語彙、段落、距離感、説明の調子 | 対象外の技術事実、数値、到達状態 |
| 説明構造のサンプル | 読みやすい技術解説、構成見本、編集方針 | 問題の置き方、概念導入、証拠と限定の配置 | 別対象の仕組み、実験結果、比較結果、固有の用語 |

作者の声と説明構造のサンプルは、対象のドメイン事実を供給しない。
特に、別のプロジェクトの概念、実験値、性能、固有の構成を、書き方が参考になるという理由だけで本文へ移さない。

一つの既存文書を根拠・事実資料と作者の声の両方に使うことはある。
その場合も、対象について言えることは根拠・事実資料としての範囲に限り、声を合わせるために内容を補わない。

## 説明プロファイル

`profile_author.py` は文長、語尾、記号などの定量的な声の手掛かりを集計する。
ソフトウェアをどう説明するかという意味的な方針は、正規表現や頻度集計だけでは決められない。

`document` モードでは、出力前に次の項目を短く埋める説明プロファイルを作る。
このプロファイルは内部の設計メモとして使ってよく、ユーザーが求めない限り逐語的に出力しない。

| 項目 | 確認する内容 |
| --- | --- |
| 読者 | 読者の役割、前提知識、読後に行う判断または作業 |
| 目的 | 設計の理解、利用判断、導入判断、調査報告、API参照など、完成物の役割 |
| 中心問い | この文書が答える一つの問い。例として「何を減らし、何を保証できないのか」 |
| 概念的骨格 | 問いを答えるために先に置く問題、考え方、仕組み、条件、根拠、限定の順序 |
| 抽象化の境界 | 本文で説明する概念の粒度と、付録や証拠表へ退避する実装詳細 |
| 識別子とコード詳細の方針 | 本文に残す公開契約、証拠アンカー、不可欠な名前と、注記へ移す内部詳細 |
| 証拠の見せ方 | 設計主張、ソース、テスト、測定、実行観測を、どの表現と表へ分けるか |
| 制約と非目標 | まだ言えないこと、比較していないこと、対象外、次の検証 |
| 用語と声 | 用語の初出説明、訳語、作者サンプルに由来する調子 |
| 資料の役割 | 各資料が根拠、作者の声、説明構造のどれを担うかと、その理由 |

説明プロファイルは、実装の事実を推定するためのものではない。
資料にない目的、読者、主張をもっともらしく埋めない。

目的または読者が欠けていても、技術的な主張の範囲を変えない安全な仮定を置ける場合は、たとえば「暫定の対象読者：このリポジトリを扱う開発者」のように明示する。
仮定が文書の構成、公開範囲、判断を実質的に変える場合や、根拠が不足する場合は、完成文を捏造せず、アウトラインと証拠の不足箇所を返す。

### 初心者向け説明プロファイル

対象読者が初心者、新入門者、非専門家である場合は、通常の説明プロファイルに [初心者向け技術説明プロファイル](beginner-explanation-profile.md) を重ねる。
これは新しい処理モードや固定テンプレートではない。
読者が何について初心者なのか、既知の足場、最小ケース、暫定的な単純化を正確さへ戻す地点、図解の可用性、数式やコードの詳細予算を決めるための追加プロファイルである。

初心者向けでも根拠段階は緩めない。
専門語を平易に導入することと、条件、例外、確度、公開識別子を削ることは別である。
比喩、図解、問いかけ、説明構造のサンプルは理解の順序を決めてよいが、対象の事実、著者固有の体験や口癖、企業や製品の情報を供給しない。

### 日本語の読み取りやすさ

日本語学習者・非母語話者向け、または「やさしい日本語」を求められた場合は、[やさしい日本語](easy-japanese.md)も使う。
対象分野に詳しい読者なら、知識の初歩を一律に説明し直さない。分野の知識と日本語力の両方に支援が必要なら、初心者向け説明と併用する。
用語と論証には[技術文書の規則](technical-writing.md)を使い、書籍用の書式は指定がある場合に限る。

### 目的プロファイル

完成物の主目的が順序付きの実行案内、原因の切り分け、複数候補の選定である場合は、通常の説明プロファイルへ対応する目的プロファイルを重ねる。

- [ガイド付きチュートリアルプロファイル](guided-tutorial-profile.md): 到達点、開始状態、操作、観察、失敗分岐、停止点、条件つき完了を管理する。
- [トラブルシューティングプロファイル](troubleshooting-profile.md): 期待と実際、観察、仮説、原因確度、権限、対応、live再検証、rollbackを管理する。
- [比較・選定プロファイル](comparison-selection-profile.md): 判断課題、必須条件、共通軸、未知、証拠条件、ライフサイクル、条件つき推奨、決定権を管理する。

目的プロファイルは、場面や読者像を置き換えない。
たとえば、初心者向けのチュートリアルでは、初心者向けプロファイルが用語と前提を橋渡しし、ガイド付きチュートリアルプロファイルが操作と確認の流れを決める。
作者サンプルは語調を決めてよいが、目的プロファイルに不足する操作、原因、順位、重み、結果を補わない。

主目的に合うものを既定で一つ選び、複合した完成物をユーザーが明示した場合だけ必要な範囲で組み合わせる。
診断依頼を修正権限へ、比較依頼を購入または導入権限へ、手順資料を実行済みの証拠へ変えない。

## 根拠段階と主張の言い方

コードや文書が存在することを、動作、性能、利用者が見た結果へ言い換えない。
次の段階を分け、本文では根拠の最も狭い範囲で述べる。

| 根拠段階 | 支えられる言い方 | その段階だけでは言えないこと |
| --- | --- | --- |
| 設計・文書上の主張 | 「設計資料はXを目的としている」「READMEはYという使い方を示す」 | 実装済み、到達可能、テスト済み、性能が出た、利用者が使えた |
| ソースの存在 | 「`src/export.py` にXを表す実装がある」「この設定項目が定義されている」 | 入口から到達する、実行される、期待どおりに働く、測定で良い結果が出た |
| 到達可能な振る舞い | 入口、構成、分岐を追い「この条件ではXを呼びうる経路がある」と説明する | 実際に実行された、すべての構成で働く、性能や利用者への効果が確認された |
| テスト・再現の証拠 | 「この条件でこのテストまたは再現手順が通った」「この失敗を再現した」 | 未検証条件での一般化、継続運用、製品品質、性能全般 |
| ベンチマーク・性能の証拠 | 「この入力、環境、計測方法ではこの値だった」 | 異なる環境での優越、全体の高速化、品質、費用対効果 |
| 実行中・利用者に見える運用 | 「この時点の実行中環境で、利用者にXが見えた」「新規起動でXを確認した」 | 恒久的な設定、すべての利用者への展開、再起動後の永続性、他環境での再現 |

テストファイルの存在は、テストが通った証拠ではない。
ベンチマーク用のスクリプトや結果ファイルの存在は、比較条件と測定値を確認するまで性能の証拠ではない。
実行ログは、記録された時点と条件の出来事を示すが、未記録の経路や利用者の画面を自動で保証しない。

本文の主張ごとに、少なくとも次を確認する。

1. 何を言いたいか。
2. どの資料が支えるか。
3. その資料は上表のどの段階か。
4. 主張の動詞と確度は、その段階を越えていないか。
5. 条件、比較対象、未検証範囲をどこで示すか。

「達成した」「示した」「利用できる」「高速である」「動作する」は、段階と条件を落とすと過大な主張になりやすい。
実際に達成済みの結果、示唆にとどまる結果、未検証の仮説や計画を分ける。

## 概念から文書を組み立てる

概念的骨格の既定候補は、次の流れである。

```text
問題または問い
  -> 動作原理
  -> 仕組み
  -> 成り立つ条件
  -> 証拠または結果
  -> 限界または非目標
  -> 次の検証または範囲を限定した定義
```

これは固定テンプレートではない。
読者、目的、利用できる資料、完成物がAPIリファレンスか設計解説かによって、順序、粒度、節の数を変える。
たとえば設計資料なら条件を仕組みの直後へ置き、調査報告なら証拠を先に見せ、APIリファレンスなら公開契約を入口にしてよい。

一般的な初稿では、まず問題と整理の軸を置く。
次に、特定のディレクトリ名や内部実装の順ではなく、分野に依存しない動作原理と仕組みを説明する。
実験、テスト、測定は、どの問いに何を示すかでまとめる。
達成済み、示唆、未検証を隣り合わせにして混ぜず、関連する既存手法や別案があるなら比較軸を明示する。
最後に、限界、次の検証、現在言える範囲を限定した定義を置く。

## コードを証拠として使う

本文に正確な識別子、型名、ファイル名、コマンドを残すのは、次の場合に限る。

- 読者がその名前を使って操作、設定、統合する
- その名前が公開API、CLI、設定、データ形式などの契約を定義する
- 根拠を追跡するための証拠アンカーになる
- 一般名へ置き換えると、対象や条件が曖昧になる

内部ヘルパー、局所変数、ディレクトリの並び、単発の呼び出し順は、通常は本文の説明を支える材料にとどめる。
読者が追跡する必要がある場合は、注記、付録、証拠表、短いコード断片へ移す。

ユーザーがAPIリファレンス、モジュール参照、デバッグ用の呼び出し経路、移行手順を求める場合は例外である。
その完成物では、公開面、モジュール、呼び出し順を中心にしてよい。
ただし例外でも、ソースの存在を実行済みの動作や性能へ言い換えない。

## 文書化の手順

1. 依頼を確認し、`document` モードが必要か、完成物の目的は何かを決める。
2. 資料を役割別に分け、根拠・事実資料だけから主張候補を作る。
3. 説明プロファイルを作り、中心問い、抽象化の境界、識別子の方針を決める。初心者向けの場合は読者プロファイルを、実行案内、原因切り分け、比較選定の場合は対応する目的プロファイルを重ねる。
4. 主張候補を根拠段階へ対応付け、達成済み、示唆、未検証を分ける。
5. 読者の問いに沿って概念的骨格を選び、本文を書き始める。
6. 本文に必要な公開契約と証拠アンカーだけを残し、コード詳細を注記や付録へ移す。
7. [保真契約](fidelity-contract.md) と次の完了監査を使って見直す。

## 完了監査

### 主張と根拠の保真

- 各主張が、設計主張、ソース、到達可能な経路、テスト、測定、実行観測のどれに支えられるか追跡できるか。
- コードの存在を、動作、速度、品質、導入済みという主張へ飛躍させていないか。
- 数値には、計測条件、比較対象、対象範囲、未測定範囲を添えたか。

### 抽象化とコードの境界

- 問題、動作原理、仕組み、条件、証拠、限界が同じ段落で混線していないか。
- 本文がディレクトリ順、モジュール順、関数順の説明になっていないか。
- 本文の識別子は公開契約、必要な証拠アンカー、曖昧さを避ける名前に限られているか。
- 余分な内部詳細は、注記、付録、証拠表へ移せるか。

### サンプルと読者

- 作者の声や説明構造のサンプルから、対象の事実、性能、到達状態を持ち込んでいないか。
- 想定読者は、中心問いへの答えと、現在言える範囲を追えるか。
- 初心者向けの場合、用語を隠さず必要性から導入し、暫定的な単純化を正確な仕組みへ戻したか。
- 実在しない図や操作を参照せず、比喩の対応関係と限界を示したか。
- 目的または根拠が不足する場合に、仮定をラベル付けしたか、アウトラインと不足資料を返したか。
- 目的プロファイルを使った場合、操作、原因、順位、重み、実行結果、承認状態を資料なしで補っていないか。
- 場面、読者、目的、作者の声の役割が混ざり、別層の規則を上書きしていないか。
