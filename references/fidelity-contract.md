# 保真契約

編集後の文章が自然でも、元の命題が変わっていれば失敗である。この文書は、編集時に保持すべき情報と検証順序を定義する。

## 基本単位

文章を単語の集合ではなく、次の関係として読む。

```text
主体 ──動作──> 対象
  │              │
  ├─時点         ├─数量・単位
  ├─確度         ├─条件
  └─根拠         └─結果・制限
```

同じ単語が残っていても、矢印の向きや修飾先が変われば意味は変わる。

## 事実台帳

長文、技術文書、報告書、学術文書では、編集前に最低限次を内部で整理する。

| 項目 | 確認内容 |
|---|---|
| 主体 | 誰、どの組織、どのシステムが行為者か |
| 動作 | 実施、検討、推定、発表、失敗など何をしたか |
| 対象 | 何に対する動作か |
| 状態 | 完了、進行中、予定、未着手、未確認か |
| 数量 | 数字、単位、範囲、比較対象、母数 |
| 時間 | 日付、期間、順序、締切、頻度 |
| 確度 | 断定、推定、可能性、仮説、伝聞 |
| 条件 | 適用条件、例外、前提、依存関係 |
| 因果 | 原因、相関、目的、結果のどれか |
| 根拠 | 出典、引用、観測、ユーザー体験 |

## 保護対象

### 数量と修飾対象

次は一組として保存する。

- `p95が480msから160msへ低下`
- `3チームのうち2チーム`
- `最大15秒`
- `約40%`
- `2026年8月時点`

誤りの例:

```text
原文: p95が480msから160msへ低下した
誤修正: レイテンシが大きく改善した
```

数字を残しても、対象が変われば失敗である。

```text
原文: 2つのチームが1つの目標を共有した
誤修正: 2回チームを変更し、1つの製品を作った
```

### 極性

次を保持する。

- できる / できない
- 含む / 含まない
- 成功 / 失敗
- 許可 / 禁止
- 有効 / 無効
- 必須 / 任意

二重否定を簡潔にしてよいが、最終的な極性を変えない。

### 確度

次は冗長語ではなく情報である。

- 可能性がある
- 推定される
- 予定である
- 見込みである
- 未確認である
- 約、およそ、最大、最小、少なくとも
- 現時点では

```text
原文: 原因はキャッシュ競合の可能性がある
誤修正: 原因はキャッシュ競合だ
```

### 時間と順序

- 過去、現在、将来
- 実施済み、進行中、予定
- Aの後にB、AとBを並行実施
- 1日ごと、週2回、連続3日

```text
原文: 来月から段階的に導入する予定
誤修正: 段階的に導入した
```

### 主体と責任

「システム」「チーム」「ユーザー」「ベンダー」「モデル」などを入れ替えない。

```text
原文: ベンダーが修正版を提供し、運用チームが適用した
誤修正: 運用チームが修正版を開発した
```

受動文を能動文へ変える場合、行為者が原文から確定できるときだけ明示する。分からない行為者を補わない。

### 因果、相関、目的

次を混同しない。

- AがBを引き起こした
- AとBが同時に観測された
- Bを目的としてAを行った
- Aの後にBが起きた
- AがBに寄与した可能性がある

```text
原文: 新UIの公開後、離脱率が下がった
誤修正: 新UIによって離脱率が下がった
```

時系列だけでは因果を確定しない。
並記、「であり」「し」だけで接続された事実からも因果を確定しない。
たとえば「審査は未完了であり、開始は許可されていない」へ、資料にない「そのため」を足さない。
原文が明示した理由や、資料で確認できる因果の接続は保持してよい。読みやすさのための接続詞が新しい主張を作っていないか確認する。

### 実装、可能性、方針

- `Xを利用できる` は `Xを利用している` ではない
- `Xの可能性を示す` は `Xで構築した` ではない
- `Xを検討する` は `Xを採用する` ではない
- `Xを目標とする` は `Xを達成した` ではない

### 出典と引用

- 引用文を言い換えない
- 引用者と発言者を入れ替えない
- URL、DOI、文献番号、ページ番号を変えない
- 出典がない主張に架空の出典を足さない
- 「研究によると」を削る場合、その研究に依存する結論を裸の事実として残さない

無源引用は場面に応じて次のいずれかにする。

- 削除しても独立して成立する判断だけ残す
- 出典不足として注記する
- ユーザーの許可がある場合だけ `[出典要確認]` を置く

### コードと構造化データ

次は原則として逐語保護する。

- コードブロック、インラインコード
- CLIコマンド、オプション、環境変数
- ファイルパス、URL、メールアドレス
- API名、型名、関数名、フィールド名
- YAML、JSON、CSV、表の値
- ログ、エラー、スタックトレース

説明文は編集できるが、データ部分を自然な日本語へ書き換えない。

### 混在資料から作るソフトウェア解説

リポジトリ、コード、テスト、既存文書、ベンチマーク出力、ログから説明文を作る場合も、資料の存在と資料が証明する内容を分ける。

- 設計資料の記述は、設計上の目的や主張の根拠であり、実装済みや実行済みの証明ではない
- ソースの存在は、その識別子や構造があることの根拠であり、入口から到達すること、テストが通ること、性能が出ることの証明ではない
- 到達可能な経路、テストまたは再現、ベンチマーク、実行中または利用者に見える運用は、それぞれ別の根拠として扱う
- 作者の声や説明構造のサンプルは、対象の実装、性能、到達状態、ドメイン事実の根拠ではない

主張ごとに根拠段階と条件を対応付け、根拠を越えた動詞へ強めない。
概念先行の文書化手順と完了監査は [ソフトウェア解説](software-exposition.md) を読む。

## 明示的に依頼された架空スレッドの演出

スレッド化や創作の依頼では、レス番号、架空の名無し名、アンカー、質問、相づち、軽い掛け合いを形式上の追加として扱える。
これらは実在の投稿、利用者の反応、専門家の見解の証拠ではない。対象の数字、確度、条件、主体、実測結果は通常どおり保存する。
元資料の測定者を架空のイッチへ替えたり、資料にない評判や実体験を話者に語らせたりしない。
資料中の引用文そのものは口語化せず、引用を紹介する周囲の会話だけを変える。
具体的な形式と監査は [なんJスレッド風プロファイル](nanj-thread-profile.md) を読む。

## 抽象度保存

具体性を加えることが常に改善とは限らない。

```text
原文: この方案は作業効率を上げる
許容: この方案で作業効率が上がる
禁止: このツールで毎日2時間節約できる
```

原文が「方案」なら、根拠なしに「製品」「ツール」「プラットフォーム」へ具体化しない。

## 情報を削除できる条件

次をすべて満たす場合に限り削除できる。

1. 同じ意味が隣接箇所に明示されている
2. 数字、条件、例外、確度、責任を含まない
3. 段落の論理接続を担っていない
4. 削除後も主張の範囲が広がらない
5. 引用や固有の声ではない

「冗長に見える」だけでは削除理由にならない。

## 明示された要約

上の削除条件は通常の文章編集に適用する。要約を明示的に求められた場合は、指定された対象へ情報を絞ってよい。
ただし、残す主張の根拠、条件、例外、否定、確度を取り除いて、元より強い主張や異なる意味にしない。
一般的な読みやすさの依頼を、情報を削る要約の権限へ読み替えない。

## 二段階監査

### Pass 1: 保真

- 保護対象の追加・脱落
- 主体と動作の関係
- 数字の修飾先
- 時制、完了状態、確度
- 因果と目的
- 出典と引用

### Pass 2: 表現

Pass 1を通過した後だけ、テンプレ表現、リズム、接続詞、記号を直す。

## 静的監査の限界

`scripts/protect_audit.py` は文字列として識別できる保護対象を比較する。次はモデルまたは人間による確認が必要である。

- 主体と責任の入れ替わり
- 因果と相関の混同
- 数字の修飾対象の変更
- 含意や前提の変化
- 固有表現の別名化
- 段落削除による論証範囲の変化
